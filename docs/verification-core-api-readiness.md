# 核心控制接口启动就绪修复

日期：2026-10-23。候选版本：0.13.1（55）。

## 现场证据与判断

11:03:59 辅助服务更新完成。11:04:04 的第一次连接被其他隧道默认路由阻止，这是保留的安全检查，不绕过。11:04:11 的第二次连接依次通过核心配置检查、进程启动、TUN 接口就绪和路由编码校验，11:04:13 在客户端首次 `/proxies` 请求处约 32 ms 后报告“核心检测失败：连接”，随后执行恢复。

确认的代码缺口是：辅助服务准备完成后，客户端仅立即请求一次控制接口；TUN 接口和代理监听就绪并不保证控制 HTTP 接口已经可用。现场表现与此时序竞争一致，但尚未通过新版实网连接确认其为唯一原因。

## 修改

- 新增 `CoreAPIReadiness`，在启动窗口内等待经过鉴权、响应格式有效的控制接口。
- `CoreAPIError` 保留结构化 URL 传输错误码；只有拒绝连接、连接暂时中断、传输超时可以在启动窗口内重试，不依据提示文字猜测。
- 重试预算默认 5 秒，间隔 100 ms；每次请求的等待参数不超过剩余预算或 1 秒。请求已进入 URLSession 后仍遵循其取消和资源超时行为；不能将此重试预算解释为对不合作底层调用的硬中断。
- 取消立即传播；鉴权、错误响应、响应格式错误不重试；超时后迟到成功不得进入网络激活。
- 等待复用现有控制会话，不关闭控制通道、不重复启动核心、不提前激活 TUN；失败仍沿用已有恢复事务。
