# 轻舟接管超时与外部代理交接：排查结果

2026-10-22。本轮没有重连轻舟、没有安装新候选，也没有直接执行路由或 DNS 写入。已在确认没有 recovery.json 后停用并卸载运行中的轻舟 launchd 服务；不删除企业路由、不重置系统代理。当前 Applications 仍是原 0.12.3（50），新源码修复尚未进入该应用。

## 当前网络

轻舟辅助服务为 disabled，未发现 QingzhouHelper 或其 sing-box 核心进程，未发现待恢复记录。系统代理仍为原来的 127.0.0.1:7897，Clash Verge 核心运行。通过该代理请求 `https://www.gstatic.com/generate_204` 返回 204，耗时约 1.29 秒。Apple 页面曾返回 200，但一次完整正文下载超过 8 秒，因此这里只确认基本 HTTPS 通道可用，不宣称全部业务恢复。

Shadowrocket 系统状态为 Disconnected，最后状态变化 22:36:02。没有强制切换当前可用的 Clash 通道，也没有重新启动 Shadowrocket 隧道。现有证据不能单独确定它当时连接失败的唯一原因。

## 已确认的等待原因

应用诊断日志：22:32:18 开始连接；核心准备 1,666 ms，接管前探测 1,447 ms；接管激活等待 60,000 ms 后失败，恢复阶段记录 12,716 ms，整次连接记录 135,851 ms。阶段记录不能完整解释所有间隙，不能把未记录部分猜测成某一个系统调用。

路由审计只剩轮转后的尾段，操作序号 9,381–11,841。尾段有 1,475 次整表采样、497 次查询及 489 次确认删除；这些操作耗时合计约 18,195 ms，单次最大 21 ms。它不是完整事务总量，也不能用尾段推算所有写入数量。恢复仍标记为 protection，说明原日志阶段归类也有缺口。

使用当前系统的只读路由快照，离线复用了正式规划代码：163 条规划路由中，103 条被识别为企业保护项；原算法把它们逐项从地址空间扣除，产生 1,227 条捕获路由。每条捕获又串行执行写前记录、整表采样、写入及核验，造成大量操作累积。之前“600 个已有保护项”的测试没有覆盖这种捕获碎片放大，这是验证缺口。

这说明当前等待有明确的算法规模问题，并不能证明之前的 kernel panic 触发链已经消除。

## 本轮源码修复

1. 保留原生后端与 CIDR 差集。已核验且更具体的企业路由本就优先于宽泛捕获，不再无条件为每个公网主机拆补集。检查所有补集碎片；若同长或更具体的捕获可能覆盖企业路由，继续差集直到收敛。4096 硬预算、作用域保护、写前记录与最终核验保留。
2. 每次新增前复用刚取得的写前快照，检查是否出现另一个隧道的公网接管；发现竞争就停止新增并恢复自有内容。没有增加高频 route/netstat 子进程。
3. 启动失败立即显示恢复阶段，恢复前不再额外发起一次可能耗尽整个预算的诊断状态请求。启动失败清理改为保留外部网络，原有实际 TUN 验证不省略。
4. 恢复审计使用 recovery 阶段，并增加操作时间戳，便于区分激活、回收及日志间隙。
