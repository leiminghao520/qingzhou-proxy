# macOS 网络重建暂态恢复

版本：0.8.12（26），日期：2026-10-17。

## 现场证据

0.8.11 已更新且实际运行的辅助服务与包内摘要相同，但仍出现真实睡眠断开。系统电源记录显示 14:22:45 进入睡眠，14:38:12 后台唤醒，14:38:57 再次睡眠，14:39:08 进入用户唤醒。应用日志在 14:38:15 记录：“网络重新激活失败：IPv6 默认路由属于其他接口，未启用 TUN；原网络已恢复”。14:39:38 手动重连后 TUN 和 HTTPS 检测通过。

本次明确的失败是重规划期间 IPv6 出口未就绪，与前次命令预算错误不同。日志不包含失败时的完整路由表，不能确认短暂出口属于哪个系统接口或隧道；修复保留对其他接口和外部 VPN 的原有检查，不假定它们都可以覆盖。

## 行为修复

- 网络重建失败先核对旧设置已恢复。只有明确标记的网络暂不可用错误才重试，使用 1、2、4、8、15、30、30 秒的有限退避；Dispatch 计时器不消耗机器睡眠期间的时间。
- 每轮继续执行完整的网络、DNS、路由、配置及外部接管检查，不忽略 IPv6 冲突，不自动改成 IPv4 或系统代理模式。实际外部接管、配置失败和恢复冲突立即终止。
- 仅为当前已授权的控制通道保留连接意图和受限模型，不写入磁盘。手动断开、恢复、退出及控制通道关闭取消待重连任务；过期回调不能重新接管。辅助服务重启也不会重建该内存会话。
- 界面将“等待网络重连”与“核心退出”分开，暂停监控也继续检查辅助服务生命周期。等待期间暂停失效的健康检查、清除旧流量和连通性结果，避免旧控制端口不可达触发第二条自动断开路径；连接重建后重新检查真实连通性。
- 辅助服务最终停止时显示其具体原因，避免一律提示“核心异常退出”。

## 0.8.13：企业路由后到的准备竞态

0.8.12 真实唤醒验收未通过：16:50:23 记录 `172.16.0.0/12` 被 `utun6` 占用，自动恢复终止。随后读取到 EasyConnect 正在运行，`utun6` 使用 `10.251.1.1` 承载企业网段，轻舟使用 `utun7`。16:50:50 手动重连后 HTTPS 检测恢复。失败时未记录完整冻结计划，不能断言是哪条准备路径触发；代码检查表明，冻结绕过计划后新出现企业路由时，正式 addRoute 会抛出永久冲突，符合该错误。

0.8.13（27）仅对冻结绕过计划的同前缀接口变化标记“网络尚未就绪”，在不写入、不认领企业路由的前提下回滚，再使用现有有限退避重新读取完整网络快照。新计划识别已有企业网段并保留其出口。准备期间企业保护路由及绕过原路径变化也触发完整重规划；普通保护写入、默认接管冲突和恢复所有权冲突仍停止。真实外部公网接管仍由完整准备检查拒绝。

新增夹具链接正式 RouteWriter 实现，禁止系统路由写入，验证企业后到网段冲突→安全回滚→新计划保留企业出口→同一连接恢复；普通保护及默认接管冲突仍拒绝。网络监控共 41 条断言通过，QingzhouChecks 共 121 场景、1258 条断言通过。真实睡眠唤醒及完整覆盖率、变异指标仍未验证。
